# Анализ нагрузок (Capacity Planning)

## Исходные допущения

| Параметр | Значение | Обоснование |
|---|---|---|
| Уникальных пользователей в сутки (DAU) | **10 000** | целевой масштаб |
| Приёмов пищи в день на пользователя | 4 | завтрак, обед, ужин, перекус |
| Продуктов на один приём пищи (в среднем) | 2 | каждый продукт логируется отдельной записью, у приёма пищи обычно не один компонент |
| **Добавлений в дневник (diary_entries) в день** | **8** | 4 приёма пищи × 2 продукта |
| Поисковых запросов на одно добавление | 2 | при ошибках |
| **Поисковых запросов в день** | **16** | 8 добавлений × 2 запроса |
| Открытий day summary в день | 6 | 3 плановых (после приёмов пищи) + 3 уточняющих (сколько осталось до нормы) |
| Редактирований/удалений записи в день | 0.5 | реже, чем добавление |
| Просмотров статистики за период | 1 раз/неделю (0.143/день) | не ежедневная операция |
| Cache hit rate по `product_cache` | 90% | после прогрева кэша частыми запросами |

## 1. Расчёт соотношения Read/Write

### Write на пользователя/день

| Операция | Кол-во | Пояснение |
|---|---|---|
| INSERT diary_entries | 8 | по числу добавленных продуктов |
| UPDATE/DELETE diary_entries | 0.5 | правки записей |
| INSERT product_cache | 1.6 | промахи кэша: 10% от 16 поисковых запросов |
| **Итого write** | **10.1** | |

### Read на пользователя/день

| Операция | Кол-во | Пояснение |
|---|---|---|
| SELECT day summary | 6 | 3 плановых + 3 уточняющих |
| SELECT по product_cache (поиск) | 16 | каждый поисковый запрос — чтение, независимо от исхода |
| SELECT статистики за период | 0.143 | раз в неделю |
| **Итого read** | **22.14** | |

### Соотношение

**Read : Write ≈ 22.14 : 10.1 ≈ 2.19 : 1**

Соотношение заметно ниже типичных 80:20 для read-heavy сервисов — ядро приложения не "потребление контента", а логирование данных пользователем, поэтому нагрузка на запись сопоставима с нагрузкой на чтение. При проектировании индексов и кэшей это нельзя игнорировать: оптимизация только под чтение здесь недостаточна.

### Агрегированно на весь DAU (10 000)

- Writes/день = 10.1 × 10 000 = **101 000**
- Reads/день = 22.14 × 10 000 = **221 400**
- Всего операций/день ≈ **322 400**, в среднем ≈ **3.73 оп/сек**

**Пиковая нагрузка** (допущение: 20% суточного объёма приходится на пиковый час + всплесковый коэффициент ×3 внутри часа):
- Пиковый час: 0.2 × 322 400 = 64 480 операций → 17.9 оп/сек в среднем за час
- Пиковое мгновенное значение: **≈ 54 оп/сек**

Нагрузка тривиальна для одного инстанса PostgreSQL на современном оборудовании; вероятный bottleneck на этом масштабе — латентность/rate limit внешнего API (Open Food Facts), а не сама БД.

## 2. Расчёт объёмов сетевого трафика

### Размеры payload (JSON, без протокольных заголовков)

| Операция | Запрос | Ответ |
|---|---|---|
| Поиск продукта | 0.1 КБ | 1.5 КБ (5–8 результатов) |
| Запись в дневник (INSERT/UPDATE/DELETE) | 0.15 КБ | 0.3 КБ |
| Day summary | 0.1 КБ | 1 КБ |
| Статистика за период | 0.15 КБ | 3 КБ (месяц точек) |

### Трафик на пользователя/день (клиент-серверный)

| Операция | Расчёт | КБ |
|---|---|---|
| Поиск | 16 × 1.6 КБ | 25.6 |
| Запись в дневник | 8.5 × 0.45 КБ | 3.83 |
| Day summary | 6 × 1.1 КБ | 6.6 |
| Статистика | 0.143 × 3.15 КБ | 0.45 |
| **Итого payload** | | **36.48** |

С учётом протокольного overhead (TCP/TLS/HTTP-заголовки, +30%):

**36.48 КБ × 1.3 ≈ 47.4 КБ/пользователь/день**

### Клиент-серверный трафик на весь DAU (10 000)

- В день: 10 000 × 47.4 КБ ≈ **474 МБ**
- В месяц: ≈ **14.2 ГБ**
- В год: ≈ **173 ГБ**

### Трафик до внешнего API (Open Food Facts)

- Промахи кэша: 1.6 × 10 000 = **16 000 запросов/день**
- Средний размер ответа продукта (полный JSON с составом и нутриентами) ≈ 10 КБ
- В день: 16 000 × 10.2 КБ ≈ **163.2 МБ**
- В месяц: ≈ **4.9 ГБ**
- В год: ≈ **59.6 ГБ**

### Итог

**Суммарный годовой сетевой объём ≈ 232.6 ГБ** (клиент-серверный + внешний API) — на порядок ниже лимитов практически любого облачного хостинга; сеть не является узким местом архитектуры даже при 10 000 DAU.
